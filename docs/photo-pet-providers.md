# Make your own pet

The native sidebar page accepts JPEG/PNG/HEIC pet photos using the existing 15 MB, dimension and pixel-count validation. Select Gemini, OpenAI or Grok, save that provider's API key in macOS Keychain, name the pet, and click Create. Each key has a separate Keychain account. Remove key deletes that credential. No provider keys are written to UserDefaults, atlas metadata, logs or PawSync's backend.

The photo is resized to a 1536-pixel maximum and re-encoded without EXIF metadata before a direct HTTPS image-edit request. The selected provider receives the photo only when Create is pressed. This is a bring-your-own-key path billed by the provider, independent of PawSync generation credits. The existing credit-backed service remains a collapsed alternative on the same page.

Request contracts were checked against official documentation on 6 October 2026:

- [OpenAI image edits](https://developers.openai.com/api/reference/resources/images/methods/edit): JSON `images[].image_url`, `gpt-image-2.5-sunburst`, one 1536×1024 PNG with transparent background, Bearer authentication.
- [Gemini image editing](https://ai.google.dev/gemini-api/docs/generate-content/image-generation): `gemini-3.1-flash-image:generateContent`, reference image in `inline_data`, image response modalities and 3:2 image configuration, `x-goog-api-key` authentication. Thought-image parts are skipped when extracting the final image.
- [Grok image editing](https://docs.x.ai/developers/model-capabilities/images/editing) and [base64 output](https://docs.x.ai/developers/model-capabilities/images/generation): `grok-imagine-image-2.0`, JSON `image` reference and base64 output, Bearer authentication.

Requests have a 180-second timeout and a 190-second resource timeout. Paid requests do not retry automatically because a dropped response can already have incurred a charge. Errors show a manual retry, clear quota/access guidance and a timeout billing reminder without echoing raw provider error bodies. Cancel stops the client request; the provider can still bill work already submitted. Responses are bounded to 48 MB; decoded images to 20 MB and 3072×2048 pixels. Redirects to another origin are refused. Only the selected provider's fixed API host is contacted; inline output avoids a second download origin.

The prompt asks for five isolated parts in a 3×2 atlas: body with hind feet, head, left forearm, right forearm, tail. The client removes a flat border-connected matte locally, preserving enclosed eye highlights and white markings, trims the parts, bounds their textures to 400 pixels and writes the existing skeletal `atlas.json` contract. Empty or overlapping parts are rejected with cleanup. Generated art is staged under Application Support/PawSync/Pets/.drafts until the user previews the assembled rig and clicks Add to my desktop. Discard deletes that draft; adding moves it atomically into the normal custom-pet library. These pets use the existing skeletal reactions rather than claiming to be authored OpenPets frame atlases. Generated faces do not receive guessed blinking overlays without eye landmarks.

`--check-photo-pet <output-directory>` uses synthetic local fixtures to verify all three request/response contracts, header separation, safe errors, final-image selection, white-detail preservation, part/texture validation, failure cleanup and native rig reactions. It never uses a real key or calls a provider. Actual photo fidelity, atlas semantics and provider account/model access require a funded user key and an end-to-end generation; image geometry checks cannot establish that a model placed the correct body part in every cell. The preview is provided for that reason.
